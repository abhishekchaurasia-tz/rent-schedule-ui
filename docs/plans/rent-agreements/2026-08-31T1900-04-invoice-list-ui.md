## Technical Approach

**One list page, one service method, one query-parameter hook on the page it links to.**

`InvoiceListComponent` at `/invoices`:

- **Filters as one `FormGroup`**, projected into query parameters by a builder that **omits every
  member the user left blank**. An empty `invoiceNumber` sent as `""` is not the same request as one
  not sent, and the endpoint would try to match it exactly.
- **Status is a multi-select of chips**, held as a `Set` of wire tokens and emitted as a repeated
  `status` parameter — the shape the endpoint unions.
- **Paging is read from the response, never computed.** `pageNumber`, `totalPages`, `hasNextPage` and
  `hasPreviousPage` all come back; recomputing them client-side would be a second source that drifts
  the moment the page size is capped or a filter changes the total.
- **Any filter change resets to page 1** before searching, because page 4 of the old result set says
  nothing about the new one.
- **`lastRefreshedAt`** is stamped on each successful response, giving the design's "last refreshed
  at …" line and making "Refresh Now" mean something visible.

**Presentation decisions that carry meaning, not just style:**

- Status maps to the design's vocabulary — `received` reads **"Fully Paid"**, which is what the
  screenshot shows, not the wire's own word.
- A row with a balance outstanding renders its money in the alert colour, matching the design, driven by
  `balance > 0` rather than by the status — a `partial_paid` row still owes money and should read that
  way.
- Payers are named with `placeholderTenantIdentity`, the derivation the other two screens already share,
  so the same tenant id is the same person across the app.
- Property and unit render as **shortened ids with the full value on hover**. Not names: this context
  holds none, and inventing them here — unlike the tenant stand-ins, which are an established
  convention in this demo app — would put fabricated property names next to real money.

**`InvoicesService.search(query)`** builds `HttpParams` from a typed criteria object, appending `status`
once per selected value. **`UpdateProposedInvoiceComponent` gains an `ngOnInit`** that reads
`?invoiceId=` and loads it, which is what turns a row into a working link.

## Technical Decisions

| # | Decision | Chosen | Alternatives rejected | Why |
|---|----------|--------|-----------------------|-----|
| 1 | Whether to modify the search endpoint | Use it as-is; add only the two derived fields (v37) | Build a bespoke list endpoint; reshape the response to the design | The endpoint already serves nine of the design's eleven columns with every filter the screen needs. Reshaping it to one screen's table would bind a general read to a particular layout. Source: user 2026-08-31 (*"agar wo implement ho jaye to better, nahi to us API ko modify kar ke"*) — it was implemented, so the smaller change won |
| 2 | The "Processing" column | Omitted, with the reason stated in the spec | Render `$0.00`; render "—" | There is no in-flight-payment state to report. A money column that always reads `$0.00` looks measured and is not — the one thing a money column must never be |
| 3 | Per-column sorting | Not offered | Render the design's sort carets as decoration; sort the current page client-side | The order is fixed server-side so offset pagination stays stable. Carets that do nothing are a lie; sorting one page of many is worse, because it looks like it sorted the result set |
| 4 | Property and unit columns | Shortened id with the full value on hover | Invent names as the tenant stand-ins do; leave blank | The tenant stand-in convention is already established and its fakeness is documented per-screen. Extending it to property names would put invented names beside real balances, where a reader has no cue that they are placeholders |
| 5 | Alert colouring | Driven by `balance > 0` | Driven by `status === 'overdue'` | A `partial_paid` invoice still owes money. Colouring by status alone would let an outstanding balance read as settled |
| 6 | Paging values | Read from the response | Compute `totalPages` from `totalCount / pageSize` | The server already sends it. Two sources for one number is how they come to disagree — and the endpoint caps `pageSize`, so the client's arithmetic can be wrong about the very case that matters |
| 7 | Empty filters | Omitted from the query string entirely | Send empty strings | `invoiceNumber=""` is an exact-match filter for the empty string, not the absence of a filter |
| 8 | Row → correction link | `/invoices/update?invoiceId=<id>`, with the target page reading the parameter on init | Copy the id to the clipboard; a modal on the list | A link is the cheapest thing that makes the correction screen reachable at all, and the target page already does everything else |
| 9 | **v2** — Where the add panel's lease comes from | **Typed** in the panel's first step | A picker of the leases referenced by the listed rows; a per-row "add fee" action | Corrected by the user mid-build: *"add new to kisi bhi agreement id ban jayega"* (2026-08-31). Sourcing it from the rows would make the one lease you most need this for — a new one with no invoices yet — the one lease unreachable |
| 10 | **v2** — One step or two | Two: id, then the fee panel | A single form with the id field above the panel | The panel cannot render before the lease loads — it needs `propertyOwnerId` for its catalog fetch and the lease dates for its candidate-date resolution. A one-form version would show an item picker that is empty until an unrelated field is filled |
| 11 | **v2** — After a successful add | Close, confirm, and re-run the current search | Leave the list alone; optimistically insert a row | The refresh is the reason to add from this screen rather than the dedicated page: a standalone one-off fee on an active lease raises its own invoice in the same transaction, so the list is stale immediately. An optimistic row would have to guess whether an invoice was raised at all — which depends on lease status, recurrence and attachment |
| 12 | **v2** — Tenant selection | Not offered here; the fee is shared by every active tenant | Duplicate the Add Additional Fee page's tenant picker into the panel | The user asked for the fee panel, not the whole page. The dedicated screen already loads the lease's tenants for exactly this, so the panel names it rather than growing a second copy of it |
| 13 | **v2** — `.banner` styles | Extracted to `src/styles.scss` | Leave three copies; raise the per-component budget | The three copies were identical, and the third one breached the 6 kB per-component budget. Raising the budget would have hidden the duplication that caused it |

## Data Model & Schema Changes

None — a client-side screen over an existing endpoint. The TypeScript delta is `InvoiceSummaryResponse`,
a generic `PagedResult<T>`, and an `InvoiceSearchQuery` criteria object, all mirroring backend contracts
that already exist.
